# Admin assistant coverage inventory

This inventory maps every current admin capability to the assistant. The assistant does **not** have full admin control: order operations beyond cancellation, purchases, returns, settings, staff, notifications, imports and reports exports are scheduled for later assistant phases (3–5).

Status vocabulary:

- **Supported and verified** — read or prepare tool, confirmation executor, audit event and tests for preparation and execution.
- **Supported, partially verified** — works, but one path (named in the row) has no dedicated test.
- **Supported but broken** — none at the time of writing.
- **Missing** — an admin capability with no assistant path and no phase assigned.
- **Deliberately excluded** — never exposed, with a reason.
- **Scheduled** — planned for a named later phase.

`ADMIN_ASSISTANT=full` only enables rows marked Supported.

Totals: 77 model tools — 23 read, 4 draft (edit only the owner's server-side product draft), 50 prepare. No generic, SQL, `execute` or `confirm` tool exists; executing a card requires the owner's tap on the card and a server-held one-time token.

Risk levels: 1 read (runs immediately) · 2 reversible content/configuration · 3 financial, stock or wide-reaching · 4 permanent deletion or access control (destructive card, acknowledgement, token issued within 2 minutes).

Test keys: **U** unit, **I** `tests/integration/database-assistant*.test.ts`, **C** `database-assistant-contracts.test.ts` (every tool: strict bounded schema, unknown/missing/mistyped input rejected, read vs full mode, structured result, no business change during preparation, no phone numbers in output, safe errors, audit), **M** migration tests, **E** `tests/e2e/admin-assistant*.spec.ts`. Every tool row below is also covered by **C**.

### Catalog items deliberately not in Phase 1

| Capability                                  | Reason                                                                                                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Additional product images, gallery ordering | The catalog and storefront have a single-image model. A gallery needs a new table and storefront UI; it is a product decision, not an assistant gap.                                  |
| Parent/child categories                     | The schema has no hierarchy. Adding one changes storefront navigation and was not requested as a schema change.                                                                       |
| Variant-level cost editing                  | Cost is derived from purchases and stock movements; editing it directly would bypass the stock ledger. Cost changes go through purchases (Phase 3).                                   |
| Variant merge                               | Rule: move the stock with a stock transfer (`prepareStockTransfer`), then archive the duplicate variant. Duplicate creation is blocked at preparation and re-checked at confirmation. |

### Phase 2 invariants

- An offer's final price is computed by `offer-pricing.ts` and must stay above zero and below the list price. The list price is never edited; orders snapshot `list_unit_price_agorot` and `offer_id`. Two enabled offers whose windows overlap (start inclusive, end exclusive) may not cover the same variant; the check runs again under an advisory lock at confirmation.
- Ledgers are append-only (database triggers). Corrections are new adjustment, correction or reversal entries.
- Merge keeps all history on the archived duplicate (`merged_into_*`); only the open balance moves, as a pair of entries, and aliases move to the target.
- Checkout refuses hidden, draft or archived products and archived variants.

### Phase 2 limitations

- After a merge the target's invoice aging does not include invoices kept on the duplicate.
- Offers apply to storefront orders; manual assistant sales use list prices.
- There is no admin offers page yet, and no basket-total offers.

## Invariants for Phase 1

- The storefront shows only `publication = 'published'` and unarchived products; archived variants never reach the storefront or new orders.
- Order and invoice lines keep their own name, label, SKU, barcode and price snapshots; catalog edits never rewrite them.
- SKU and barcode are unique among active variants (case-insensitive SKU). The check runs at preparation and again under an advisory lock at confirmation.
- A category with active products cannot be archived; a category referenced by any product (including archived) or by a merge cannot be deleted.
- The default variant cannot be archived or deleted; a variant with stock on hand cannot be archived.
- Opening stock always carries a unit cost and is written as an `opening_balance` movement in the same transaction as the product.
- Prices, costs and stock values are integer agorot / milli-units computed by services; the model never supplies a total.

## Reliability layer (applies to every row)

| Concern                   | Mechanism                                                                                                                                                                                           | Tests                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Invented business figures | Each reply is checked against the tool results of the same request and the owner's message; an amount or quantity that appears in neither is replaced with a fixed Arabic reply.                    | U `grounding.test.ts`, E `admin-assistant-reliability.spec.ts` |
| Premature success claims  | Chat never executes changes; any «تم/انضاف/تعدّل/انحذف/تم الدفع» claim in chat is replaced. Completion is reported only by the card after the confirmation endpoint commits.                        | U, E                                                           |
| Explicit result states    | Prepare outputs carry `state`: `needs_clarification`, `ready_for_confirmation` or `unsupported`; the confirmation endpoint returns `confirmed_and_completed`, `confirmation_failed` or `cancelled`. | U, C                                                           |
| Prices in Arabic forms    | One server parser (`parseMoneyInput`) for assistant inputs and admin forms: digits, `₪`, شيكل/ش, decimal dot or comma, Arabic-Indic digits and a tested set of number words.                        | U `money-input.test.ts`, E                                     |
| Ambiguity                 | Identifiers and exact names resolve; partial or fuzzy matches always become choices before any change.                                                                                              | U, I                                                           |
| Interrupted streams       | Unfinished tool calls are stored as explicit interrupted errors; the message is marked `interrupted` and offers a retry; broken stored conversations are repaired on load.                          | U, E (real reload mid-stream)                                  |
| Loops                     | The agent stops on an identical repeated tool call or two failing steps; temperature 0 for non-reasoning models; output capped.                                                                     | U                                                              |
| Errors                    | Stable codes; Arabic messages; chat failures carry a short support reference; provider and database messages are never shown.                                                                       | U, C                                                           |
| Prompt injection          | Attachment, packaging and tool text is untrusted data; image reads never fill fields below 0.7 confidence; no tool can confirm.                                                                     | I, C                                                           |
