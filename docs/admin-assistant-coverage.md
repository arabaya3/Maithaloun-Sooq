# Admin assistant coverage inventory

This inventory maps every current admin capability to the assistant. A row is **Supported** only when a read tool or a prepare tool, a confirmation handler, an audit event and tests exist. Everything else is either scheduled for a named phase or explicitly excluded with a reason. `ADMIN_ASSISTANT=full` only enables the rows marked Supported.

Risk levels: 1 read (runs immediately) · 2 reversible content/configuration · 3 financial, stock or wide-reaching · 4 permanent deletion or access control (destructive card, acknowledgement, token issued within 2 minutes).

Test keys: **U** unit, **I** `tests/integration/database-assistant*.test.ts`, **M** `database-catalog-migration.test.ts`, **E** `tests/e2e/admin-assistant*.spec.ts`.

### Catalog items deliberately not in Phase 1

| Capability                                  | Reason                                                                                                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Additional product images, gallery ordering | The catalog and storefront have a single-image model. A gallery needs a new table and storefront UI; it is a product decision, not an assistant gap.                                  |
| Parent/child categories                     | The schema has no hierarchy. Adding one changes storefront navigation and was not requested as a schema change.                                                                       |
| Variant-level cost editing                  | Cost is derived from purchases and stock movements; editing it directly would bypass the stock ledger. Cost changes go through purchases (Phase 3).                                   |
| Variant merge                               | Rule: move the stock with a stock transfer (`prepareStockTransfer`), then archive the duplicate variant. Duplicate creation is blocked at preparation and re-checked at confirmation. |

### Phase 2 invariants

- An offer's final price is computed by `offer-pricing.ts` and must stay above zero and below the list price. The list price is never edited; orders snapshot `list_unit_price_agorot` and `offer_id`. Two enabled offers whose windows overlap (start inclusive, end exclusive) may not cover the same variant; the check runs again under an advisory lock at confirmation.
- Ledgers are append-only (database triggers). Corrections are new adjustment, correction or reversal entries.
- Merge keeps all history on the archived duplicate (`merged_into_*`); only the open balance moves, as a pair of entries, and aliases move to the target.
- Checkout refuses hidden, draft or archived products and archived variants.

### Phase 2 limitations

- After a merge the target's invoice aging does not include invoices kept on the duplicate.
- Offers apply to storefront orders; manual assistant sales use list prices.
- There is no admin offers page yet, and no basket-total offers.

| Capability                                                                                                  | Reason                                                                                                 |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Login, logout, password change                                                                              | Session and credential flows must stay in the authenticated UI; the assistant never handles passwords. |
| Generic SQL, generic record deletion, HTTP requests, environment variables, cron expressions, `CRON_SECRET` | Security boundary: every operation is a narrow, validated domain tool.                                 |
| Promoting anyone to owner, removing the last owner, API keys                                                | Access-control invariants; not exposed even in later phases.                                           |
| Legacy voice command flow (`/admin/voice`)                                                                  | Superseded by voice input in the assistant composer; kept for operators, not duplicated as tools.      |

## Invariants for Phase 1

- The storefront shows only `publication = 'published'` and unarchived products; archived variants never reach the storefront or new orders.
- Order and invoice lines keep their own name, label, SKU, barcode and price snapshots; catalog edits never rewrite them.
- SKU and barcode are unique among active variants (case-insensitive SKU). The check runs at preparation and again under an advisory lock at confirmation.
- A category with active products cannot be archived; a category referenced by any product (including archived) or by a merge cannot be deleted.
- The default variant cannot be archived or deleted; a variant with stock on hand cannot be archived.
- Opening stock always carries a unit cost and is written as an `opening_balance` movement in the same transaction as the product.
- Prices, costs and stock values are integer agorot / milli-units computed by services; the model never supplies a total.
